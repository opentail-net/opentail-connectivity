# External code review, 2026-10-20: findings and fixes

An outside review (ChatGPT, reading `main` remotely, no local build) reported 8 numbered findings and 5 smaller ones. Each one
was checked against the code at `eb50234`. **All 13 hold.** Checking them turned up 7 more (marked **new**). Everything except E2
was fixed on 2026-10-20 (see plan section 22). E2 was fixed in the second-review pass. R3 was decided as (a), fail closed.
**All findings are fixed.**

**How exposed we are today.** The Host does not reference `MemoryRetriever`, `VectorDataMemoryBackend`, the email approval
classes, or the SQLite, folder, crawl and Reddit connectors (grep of `opentail-host`, 2026-10-20). So nothing here is live
in a Host deployment. These are bugs in the library's contract. Memory items R1 and R2 must be fixed before memory M7 wires
retrieval into the Host. E1 and E2 must be fixed before any Host tool exposes approvals.

Line numbers refer to `eb50234`.

## 1. Memory security (blockers)

### R1. A request scope widens permissions *(confirmed)* ✅

`OpenTail.Connectivity.Memory/Retrieval/MemoryRetriever.cs:197-202` adds `request.PermissionScope` to `access.Scopes`. The
`MemoryFilter.Scopes` doc (`IMemoryBackend.cs:31`) says these are "scopes the caller holds". A caller holding `sales` who asks
for `finance` therefore gets `finance`. **New:** with `access == null`, the request scope alone grants access.

**Fix.** `access` is the ceiling. A request may only narrow it:
- If `request.PermissionScope` is set and `access.Scopes` contains it (case-insensitive, trimmed): `Scopes = [that scope]`.
- If it is set and not held, return no hits and add one `withheld["permission-scope"]`, the same reason governance uses. Never
  name the scope back to the caller.
- If `access` is null, a request scope grants nothing. Treat it as "no scopes held".
- Review the other `filter.X ?? request.X` lines (`Workspace`, `ProjectScope`, `RepositoryScope`, time window) with the same
  rule. They only narrow today, but write that down in a comment so the next field added follows it.

**Tests** (`MemoryRetrieverTests`):
- A `finance` record, `access.Scopes = [sales]`, request `PermissionScope = finance`: no hits.
- The same with `access = null`: no hits.
- `access.Scopes = [sales, finance]`, request `sales`: only `sales` records come back.

### R2. Sensitive text before redaction *(confirmed, two leaks)* ✅

1. **Reranker input.** With `IncludeSummaries` on, the backend filter drops `MaxSensitivity` (line 53). Candidates then go to
   `IReranker.RerankAsync` (lines 75-76) as `BackendHit`s carrying `Text` and the full `Record`. Governance runs only after that
   (line 88). **New:** the reranker also sees records that governance will deny for other reasons (expired, tainted, other
   scope), whenever the backend's own filtering is looser than `MemoryGovernance.Deny`.
2. **Returned record.** Line 123 builds `MemoryHit(record, …, text, …)` with the original `record`, so `hit.Record.Content`
   (and `Summary` when `AllowSummarization` is false) still holds the withheld text.

**Fix.**
- Before ranking, run `MemoryGovernance.Deny(record, sensitivityFree, now)` on every candidate, count the withheld ones, and
  decide each candidate's disposition (Allowed / Redacted / Summarized). Then rank and rerank only what survives. The final
  loop keeps a governance call as a belt-and-braces check.
- For a Redacted or Summarized candidate, the reranker gets a `BackendHit` whose `Text` is the substituted text (summary or
  empty) and whose `Record` is the redacted copy described next. It never gets the original.
- Add `MemoryRecordRedaction.Redact(MemoryRecord, disposition)`. It returns `record with { Content = "", Summary = allowed ?
  Summary : null }`, plus any other free-text field found when writing it (check `MemoryRecords.cs` for title, metadata values
  and entity text). Policy, ids and source stay, because callers need them for citation and governance. `MemoryHit.Record`
  is always the redacted copy unless the disposition is Allowed.
- Update the `MemoryHit` doc: `Record` is the record *as the caller may see it*.

**Tests:**
- A Secret record, caller limit Internal, `IncludeSummaries` on. A recording reranker gets no `BackendHit` whose `Text` or
  `Record.Content` contains the secret marker.
- The same record: `hit.Text`, `hit.Record.Content` and `hit.Record.Summary` (with `AllowSummarization = false`) don't contain
  the marker. Serialise the whole `MemoryRecallResult` to JSON and assert the marker is absent.
- An expired record and a tainted one (with `IncludeTainted = false`) never reach the reranker.

### R3. A record with no ACL skips the ACL check *(confirmed; severity raised)* ✅

`MemoryGovernance.cs:44` checks the ACL only when `record.Source.Acl` is non-null. The comment at line 82 says "Absence is not
permission: an ACL the connector did not read restricts". That holds only for an `Acl` with `Captured = false`, not for a null
one. `MemorySource.Acl` defaults to null (`MemoryRecords.cs:154`), so every record written without an ACL is visible to every
caller who passes the other checks.

**Decision needed (owner).** What does null mean?
- **(a) Fail closed (recommended).** Null is treated like `Captured = false` and denied (`"acl-not-captured"`). Records with
  no ACL concept (the agent's own notes, user preferences) must then say so explicitly, with a new `MemorySourceAcl.NotApplicable`
  (`Captured = true, Visibility = "organisation"`) or a narrower "owner" visibility. This changes behaviour for existing
  callers, so it needs a release note, and the conformance suite and quality corpus have to set ACLs.
- (b) Null means "not applicable". Keep the code and fix the comment and docs instead. That is cheaper, but it leaves the
  default open.

**Tests:** a null-ACL record is denied under (a). `NotApplicable` is allowed. The existing ACL tests still pass.

## 2. Email safety

### E1. Rate limit race *(confirmed)* ✅

`OpenTail.Connectivity.Files/Inbox/PolicyEnforcingEmailSender.cs`: `EnforceRateLimits` (95-121) checks under the lock and
releases it. The send happens at line 48 and `RecordSend` at line 49. N concurrent calls with `MaxEmailsPerHour = 1` can all
send. **New:**
- In approval mode, line 41 checks the limits at queue time, but nothing is ever counted. Approved sends go through
  `EmailSendApprovalService`'s raw sender (below), so the limits never trip in that mode.
- Windows use `DateTimeOffset.UtcNow`, so tests cannot control time.

**Fix.**
- `TryReserve()` checks and increments in one lock and returns a reservation. On send failure, `Release(reservation)` gives
  the slot back only when the provider definitely did not accept the mail (an exception thrown before the request went out).
  An ambiguous failure, such as a timeout or a 5xx after upload, keeps the slot. Over-counting is the safe direction.
- Pull the counters behind `IEmailRateLimiter` (in-process default). That is the seam the class comment already promises for a
  shared store. Take a `TimeProvider`.
- The approval path reserves at *approval* time, through the same limiter (see E2), not at queue time.

**Tests:** `MaxEmailsPerHour = 1`, a blocking fake sender, 10 parallel `SendAsync` calls: exactly one reaches the inner sender
and nine throw `EmailSendPolicyException`. Also: a failure before the request releases the slot, and an ambiguous failure
keeps it.

### E2. Double send on approval; silent persistence *(confirmed)* ✅

`EmailSendApprovalService.ApproveAsync` (20-41) does get, check `pending`, send, then mark `approved`. Two concurrent approvals
both send. `InMemoryPendingSendStore.PersistAsync` (61-78) swallows every exception, so a send can succeed while the file still
says `pending`. After a restart the same mail is approvable again. **New:**
- `LoadFromFile` (48-59) swallows a corrupt file and starts empty, losing every queued approval without a word.
- The store writes a fixed `path + ".tmp"`, not the shared `AtomicFile` that section 10 of the plan made standard for the
  other stores.
- The final `UpdateStatusAsync(..., ct)` uses the caller's token. A cancellation after a successful send leaves the record
  `pending`.
- Approval sends bypass the recipient and rate policy entirely, through `_rawSender`. Policy is checked only when the mail was
  queued, and it may have changed since.

**Fix.**
- `IPendingSendStore.TryTransitionAsync(id, from, to, note)` is a compare-and-set that returns false when the current status is
  not `from`. The in-memory store implements it with a per-record lock or `ConcurrentDictionary.TryUpdate`.
- The flow is `pending → sending` (claim; only the winner continues), then re-check policy and reserve a rate slot (E1), then
  send, then `sending → sent`, or `sending → failed` when the failure is known, or `sending → unknown` when it is ambiguous.
  `unknown` is never re-sent automatically. A human resolves it, by checking Sent Items, or by re-sending with the same
  idempotency key where the provider supports one (Graph and Gmail: check what they offer and note it in plan section 9).
- On startup, a record found in `sending` (crashed mid-send) becomes `unknown`, not `pending`.
- Persistence failures throw. A failed claim persist aborts before sending. A failed final persist is logged and returned as
  an error that says the mail *was* sent.
- Status writes after the send use `CancellationToken.None`.
- Use `AtomicFile`. A corrupt file is renamed aside (`.corrupt-<timestamp>`) and loading throws, or at least reports it. It
  never silently starts empty.
- State the guarantee in the docs: **at most once from this store's point of view; exactly-once is not promised.**

**Tests:** two parallel `ApproveAsync` calls with a blocking fake sender: one send, and the loser gets
`InvalidOperationException`. A store whose persist throws makes `ApproveAsync` fail before sending. A record left in `sending`
loads as `unknown`. A corrupt file is not silently emptied. Cancellation after the send still records `sent`.

## 3. Data integrity

### D1. Vector upsert and bulk delete *(confirmed)* ✅

`OpenTail.Connectivity.Memory.VectorData/VectorDataMemoryBackend.cs:150` deletes the old rows before embedding (155) and
writing (159). A failure in either step loses the record. `DeleteRowsAsync` (314-327) does one `GetAsync(where, GetLimit =
10_000)` and deletes what came back, so more than 10,000 matching rows (chunks of one record, or a document or collection
delete) leaves rows behind and under-reports the count.

**Fix.**
- Upsert: embed and build the rows first. Then upsert the new rows, whose keys are chunk ids, so rows with surviving ids are
  replaced in place. Last, delete the old rows of this record whose keys are *not* in the new set. A crash between the steps
  leaves extra old chunks, never a missing record. Extra rows are still governed, because they carry the same `RecordJson`.
  Note: if the new `RecordJson` changes policy, the stale rows still carry the old policy until the delete runs. Make the
  stale delete run even on cancellation (`CancellationToken.None`).
- Delete: loop `GetAsync` then `DeleteAsync` until a page comes back empty. Deleting shrinks the result, so no skip is needed.
  Add a guard on the number of iterations.

**Tests:** an embedding generator that throws on the second upsert: the first version is still retrievable. A failing
collection upsert: the same. A delete of 10,001+ rows (use the in-memory VectorData connector; mark the test slow if needed)
leaves zero.

### D2. Folder connector state snapshot *(confirmed)* ✅

`OpenTail.Connectivity.Files/Connectors/FolderSourceConnector.cs:16,34` loads `_loadedState` once in the constructor. The
comparisons at lines 70-72 and `NotProcessed` (134) always use that first snapshot. A reused instance rediscovers everything
changed since construction, every run.

**Fix.** Load the state at the start of `DiscoverAsync` into a per-run field, and use that same field in `NotProcessed`.
Store loads are cheap (one JSON file). Check whether the other connectors with a constructor-loaded state follow the same
pattern (grep `stateStore?.Load()`) and fix them the same way.

**Test:** one instance, two runs with `SaveStateAsync` in between and no file changes: the second run discovers nothing.

## 4. Smaller bugs and boundaries

### B1. Reddit name trimming *(confirmed)* ✅

`OpenTail.Connectivity.Social/Reddit/RedditConnector.cs:31`: `TrimStart('r','/')` turns `rust` into `ust` and `/r/rust` into
`ust`. **Fix:** trim whitespace, strip one leading `/`, then one `r/` (case-insensitive), then reject an empty result.
**Tests:** `rust`, `racing`, `r/marketing`, `/r/marketing`, `/marketing`, `R/rust`, `r/` (throws).

### B2. SQLite connector is read-only only by configuration *(confirmed)* ✅

`OpenTail.Connectivity.Sql/SqliteSourceConnector.cs:38,111` opens `_config.ConnectionString` as given. `BuildQuery` (165-171)
runs `TableOrQuery` verbatim when `IsQuery` is set. Lines 148 and 153 also wrap it as a subquery in fetch.

**Fix.**
- Build the connection string through `SqliteConnectionStringBuilder` and force `Mode = ReadOnly`. If the caller set
  `ReadWrite` or `ReadWriteCreate`, throw rather than silently override. That makes misconfiguration visible.
- Also run `PRAGMA query_only = ON` after opening, as a second guard, because `Mode` doesn't cover attached databases.
- Document in `SqlConnectorConfig.IsQuery` that the query is trusted operator configuration and must never come from a model
  or end user. When the Host exposes SQLite, its profile must take the query from operator config only, as the Host's Sql
  guard already does for SQL Server.

**Tests:** an `INSERT`/`DROP` passed as `TableOrQuery` with `IsQuery` fails and leaves the database unchanged. A
`Mode=ReadWrite` connection string is refused.

### B3. `IncludeDeleted` does nothing *(confirmed)* ✅

`MemoryRetrievalRequest.IncludeDeleted` (`MemoryRetrievalContracts.cs:42`) is never read, and `MemoryGovernance.cs:17` always
denies deleted records. **Fix (recommended):** mark it `[Obsolete("Deleted records are never recalled.")]` now and remove it
in the next minor release. An admin path to deleted records belongs in the Host's audit tooling, not in recall.

### B4. Folder links and item ids *(confirmed)* ✅

`EnumerateFiles` (86-118) follows directory symlinks and junctions. A junction loop recurses until the path gets too long
(**new**). `FetchAsync` (125-126) reads any `item.Id`, with no check that it lies under the root. **Fix:** skip directories (and
files, by option) with `FileAttributes.ReparsePoint` by default, with an opt-in `FollowLinks` that tracks visited canonical
paths. In `FetchAsync`, resolve `Path.GetFullPath(item.Id)` and require it to be under `_folderPath` plus a separator.
**Tests:** a junction loop terminates. A link out of the root is skipped. `FetchAsync` with `..\..\secret` throws.

### B5. Crawler origin, redirects and size *(confirmed)* ✅

`OpenTail.Connectivity.Web/SiteCrawlConnector.cs:186` and `SitemapParser.cs:75,91` compare `Host` only, so
`http://site:8080` and `http://site` count as the start origin. Pages are read with `ReadAsStringAsync` (135) and
`GetStringAsync` (122), with no size cap. Redirects are whatever the caller's `HttpClient` does. **New:** `FetchAsync` on a
cache miss fetches `item.Id` with no origin check at all.

**Fix:** compare scheme, host and port, allowing http→https on the same host as an option. Use
`HttpCompletionOption.ResponseHeadersRead`, check `Content-Length`, and read through a stream capped at
`WebCrawlOptions.MaxResponseBytes` (default 5 MB). Check the final `response.RequestMessage.RequestUri` against the origin
(this catches redirects without owning the handler). Apply the origin check in `FetchAsync` too. Document that callers who
care should pass a handler with `AllowAutoRedirect = false` or a redirect limit.
**Tests:** a different port is not followed. A redirect off-origin is dropped. An oversized body is cut off or skipped and
counted in `FailedFetchCount`.

### B6. Cursor store single writer *(confirmed)* ✅

`OpenTail.Connectivity.Files/Connectors/FileSyncCursorStore.cs:12` serialises with a per-instance `SemaphoreSlim`. Two
instances or processes on one file can lose each other's updates (each reads, modifies and writes the whole file).
**Fix (recommended):** document single-writer and enforce it. Hold a `FileShare.None` lock file (`<path>.lock`) for the
read-modify-write, and retry briefly when it is busy. Full cross-process compare-and-set is not worth it for a file store.
Deployments that need several writers should use a database-backed `ISyncCursorStore`. Apply the same lock to the inbox and
folder state stores, which share the pattern.
**Test:** two store instances on one file, interleaved updates to different scopes: both survive.

### B7. Found while checking *(new, small)* ✅

- `SqliteSourceConnector.cs:99,122`: a row with a NULL id gets `Guid.NewGuid()`, so it is a new item on every run. Use
  `row:<n>`, as the CSV connector does since section 10, or skip the row with a warning.
- The rate limiter and pending store use `DateTimeOffset.UtcNow` directly. Inject `TimeProvider` (it's part of E1 and E2).

## Tests that would have caught these

The suite tests the normal path. Add a few habits along with these fixes:
- **Governance tests assert on the whole returned object.** Serialise it and search for the secret marker, rather than
  checking one property.
- **Every gate gets a parallel test** (rate limits, approvals, stores) with a blocking fake, not only sequential calls.
- **Every write path gets a failure-injection test** (embedder throws, store throws, persist throws).
- **Reused-instance tests** for connectors that keep state.

## Release note items

R1 and R3(a) change what callers see. Under R1 a request scope no longer grants access. Under R3(a) records without an ACL are
denied unless they are marked `MemorySourceAcl.OrganisationWide`. B2 refuses read-write SQLite connection strings, and B3 obsoletes a property.
That is a minor version bump, 0.3.0.
